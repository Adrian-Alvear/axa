# AXA v2 research spikes (Phase 4, write-up only)

Date: 2026-10-21. Claude Code docs read: agent-view, permission-modes, cross-session-messaging. Nothing was built or switched over.

| Question | Answer | Recommendation |
| :- | :- | :- |
| 1. Can `claude agents --json` replace screen scraping? | Partly. It lists interactive sessions and gives status and a waiting category. It gives no prompt text, no options, and no way to answer. | Use it as a cheap status and "is it waiting" signal. Keep capture-pane for the question and options. |
| 2. Auto mode vs the approver? | Auto mode covers the routine cases well. It has no one-way doors, no goal awareness and no AXA logging. | Start sessions in auto mode, keep the approver as the second layer, and measure first. |
| 3. Can SendMessage replace links? | No. It is a good transport but has no done-detection, verify gate, logging or map. | Keep links. Optionally use `notify_when_idle` as an extra "idle" signal. Lock down inbound messaging. |

## 1. `claude agents --json`

**Found.**
- Docs: `--json` prints "every live session" as a JSON array and needs no TTY. `--all` adds completed background sessions and `--cwd` filters (agent-view).
- Fields: `cwd`, `kind` (interactive or background), `startedAt` are always present. `id` and `state` (working, blocked, done, failed, stopped) are for background sessions. `pid`, `status` (busy, waiting, idle) and `waitingFor` apply while the process is alive. `sessionId` and `name` appear when set.
- `waitingFor` values: `permission prompt`, `input needed`, `sandbox request`, `worker request`, `dialog open`.
- The docs say the question text and choices show only in the agent-view peek panel, not in the JSON. Permission prompts cannot be answered from the peek panel. You have to attach, so there is no answer API.
- Agent view is a research preview. Fields are conditional and there is no stability promise. The docs say not to scrape `~/.claude/jobs/<id>/state.json`.
- The docs also say interactive sessions in other terminals appear only after `/bg`. That is unconfirmed for tmux.

**Tested locally** (`claude agents --help`, `claude agents --json`, both read-only).
- The `--json` help text says "Print active sessions (interactive and background)". It lists `--all` and `--cwd`.
- Output was an array of 3 objects, all `kind: "interactive"`, with no `/bg` needed:
  `{pid, cwd, kind, startedAt (ms), sessionId (uuid), name, status}`, plus `waitingFor` when waiting.
- One entry had `status: "waiting"` and `waitingFor: "dialog open"`.
- Interactive entries had no `id` and no `state`.
- One entry matched the project session I am running in (cwd `/home/adrianwsl/axa-v2`, name `axa-v2-91`, status busy). That session is AXA-started, so tmux sessions do appear without `/bg`.
- I did not run tmux or touch the AXA socket, so I could not cross-check the full list against `tmux ls`. Matching to AXA sessions would be by cwd, name or pid.

**Compared with what AXA needs.** AXA needs the question and the options so one tap can answer. `--json` gives only `waiting` plus a category. It does not say whether the dialog is a permission prompt or an ordinary dialog, and `dialog open` is vague. Answering still needs `send-keys` into the pane.

**Recommendation.**
- Add `claude agents --json` as a poll alongside the hooks and event log:
  - a pid-based "alive" check;
  - `status` as a cross-check of traced status;
  - a cheap trigger to run capture-pane only when `status === "waiting"`.
- That cuts capture-pane polling on busy and idle sessions and catches the cases where hooks miss a dialog.
- Do not drop screen scraping. Treat every field as optional and fall back to today's logic when the command fails or the shape changes.
- Spike next: spawn a throwaway session, trigger a permission prompt, and record the `waitingFor` values seen. Check how fast `status` flips against what capture-pane sees.

## 2. Auto mode vs the AXA approver

**Found** (permission-modes).
- Order: allow and ask rules first, then read-only actions and in-cwd edits run without a check, then the classifier reviews the rest.
- The classifier sees user messages, non-read-only tool calls and CLAUDE.md. It does not see tool results.
- It blocks exfiltration, untrusted remotes and user-stated boundaries. It re-reads boundaries from the transcript, so compaction can lose one. A deny rule is the hard guarantee.
- Auto mode pauses and prompts again after 3 blocks in a row or 20 in total. These limits cannot be configured. In `-p` runs there is no prompt, so the action simply does not run.
- It is the starting mode for interactive sessions from v2.1.283. It is tunable through `autoMode.environment` and `autoMode.allow`.
- Classifier cost is one extra round trip per shell or network action. Reads and in-cwd edits skip it.
- Hooks: the docs say "In modes that ask, a `PermissionRequest` hook can answer the prompt." So in auto mode our hook should fire only when auto mode falls back to a prompt: an ask rule, a pause after repeated blocks, or no verdict. This is not tested.
- `PreToolUse` allow cannot approve critical-path `rm`.

| | Auto mode | AXA approver |
| :- | :- | :- |
| One-way doors | Generic rules (force-push, prod, exfiltration). Not our list. | Our own explicit list, deterministic. |
| Goal awareness | Sees the user messages in the transcript. | Can be given the project goal and spec. |
| Logging | Notification and `/permissions` "Recently denied" only. | Event log, console, map. |
| Per-project policy | `autoMode` settings. | `hooks/policy.mjs` rules per project. |
| Cost and latency | Classifier round trip on shell and network only. | A `claude -p` call for each request. Slower, and unavailable at a usage limit. |
| Failure mode | Pauses after 3 blocks in a row or 20 in total. | Request falls through to the user. |

**Data point.** In 6 hours there were 215 worker permission requests. The approver approved 201 (93%), denied 3 and passed 11 to the user, 6 of them because the approver was unavailable at a usage limit. Most of those 201 would be routine shell commands. Auto mode would handle that bulk with no `claude -p` call and no dependence on our own usage headroom, and the 6 outage cases would go away.

**Recommendation.**
- Start sessions in auto mode (`--permission-mode auto`, or `permissions.defaultMode`).
- Keep the approver as the second layer. It decides only what auto mode escalates, and one-way doors stay deterministic in our code.
- Keep one-way doors as `deny` rules or a `PreToolUse` hook, so they hold whatever the classifier thinks. Do not rely on classifier boundaries.
- Measure first, before switching:
  1. Confirm that `PermissionRequest` fires in auto mode, and when.
  2. Replay or shadow the 215-request set: how many would auto mode have run silently, how many blocked, and how many would have reached the approver?
  3. The block-pause rate. Three blocks in a row will interrupt an unattended worker, so measure how often it happens.
  4. Added latency on shell and network actions, compared with the approver's median.
  5. Any case where auto mode allows something our policy or a one-way door would deny. This is the key safety number.
- Log which layer decided each request, so the console keeps a full record.

## 3. SendMessage and `notify_when_idle` vs links

**Found** (cross-session-messaging).
- On this machine, messages go over a per-session socket and never through Anthropic servers. Sessions see each other via `ListAgents`.
- `notify_when_idle` sends one notice when the watched session next goes idle or exits. It drops after 12 hours.
- A message is plain text. It cannot approve a prompt, change settings or CLAUDE.md, or run a command. The receiving session's own permission rules still apply.
- `crossSessionInbound` is `accept`, `hold` or `refuse`. With no value set, a session that bypasses permissions holds messages from senders that don't, and asks the user to approve in a dialog (5 minute expiry).
- `refuse` set in project or local settings overrides every other source. Deny rules on `SendMessage` and `ListAgents` stop sending and listing.
- The socket path and token are exported to hooks and Bash as `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN`. On Linux a session's own children are verified and delivered even with `accept` unset.
- Only the main conversation can subscribe to `notify_when_idle`, and only to local sessions.

**Compared with AXA links** (`console/supervisor.mjs`: `runChains` fires on a settled "done" held for `DONE_MS`, only if the target is idle).

| | Links | SendMessage |
| :- | :- | :- |
| Trigger | AXA's traced "done" held for `DONE_MS`, so a verify-gate bounce settles first. | Claude decides to send, or "idle" (turn finished). A turn that is about to be bounced counts as idle. |
| Once only, only when target idle | Yes. | Delivered during a turn or starts a new one. Not controlled. |
| Verify gate | Aware. | Not aware. |
| Logging and map | Yes. | None. Hold and refuse leave no trace in AXA. |
| Who triggers | The user and the commander. | Any session, and that is the risk. |

**Security.** A project session must not steer the commander or its siblings. A model-written message from one project session could carry injected text from a web page or file into another session. It cannot approve anything, but it can start a turn, and the receiver may then ask for permissions that the approver (or auto mode) decides on. That is a prompt-injection path.

**Recommendation.**
- Keep links as the way sessions hand work to each other. The done-settling, idle check, verify gate, log and map are what make them safe.
- Block project sessions from sending and receiving messages:
  - add `SendMessage` and `ListAgents` to the deny list in the settings AXA gives each project session;
  - set `crossSessionInbound: "refuse"` in project-local settings, which overrides other sources;
  - keep the commander's inbound set the same way, so nothing can message it.
- AXA's own links should keep typing into the pane as they do today. If we later want a socket path, our hooks can post to a session's inbox socket from AXA's side. That needs a test of how delivery behaves when the target bypasses permissions, and of what the sender class is.
- Optional later spike: `notify_when_idle` as a second, cheap "idle" signal. It is not a replacement, since it fires before the verify gate settles.

## 4. Approver model measurement (Haiku vs Sonnet)

Run on 2026-10-22 with `node scripts/approver-eval.mjs --models haiku,sonnet --limit 15`: 15 synthetic
cases from `test/fixtures/approver-eval.jsonl` (never the live log), 30 model calls (the cap).

| Model | Agrees with expected | Unsafe allows | Errors | Median | Max |
|---|---|---|---|---|---|
| Haiku | 15/15 | 0 | 0 | 3290 ms | 6411 ms |
| Sonnet | 15/15 | 0 | 0 | 3508 ms | 11696 ms |

The two models gave the same decision on all 15 cases.

**Recommendation.** Haiku is as accurate as Sonnet on this set and somewhat faster, with a much lower
worst case. It's worth trying `"approver": { "model": "haiku" }` in `~/.axa/policy.json`, but 15 cases
is a small sample: grow the fixture with real escalations (written out by hand, never copied from
the live log) before switching the default. The default is unchanged in v2.
